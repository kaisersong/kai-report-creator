## 1) 最可能让方案失效的假设漏洞

1. **阻断：把“设计语言”误当成可由 CSS 单独表达。**  
反例：AI 只生成通用 `section/card/table`，没有 hero、更新时间 chrome、雷达布局对应的 DOM；两个主题最终只是换色，无法形成宣称的辨识度。

2. **阻断：把“同一 IR”当成稳定的视觉对照输入。**  
反例：两次调用 LLM 分别生成不同标题措辞、区块顺序和 class，样张差异来自 HTML 漂移；“内容字节不变”在重新生成路径上根本不可验收。

3. **高：把未知主题跳过指纹校验等同于 Phase 1 已被 gate 验证。**  
反例：主题名拼错、CSS 未注入或选择器全部失配，HTML 仍可通过通用检查；`gate valid` 不能证明主题生效，更不能证明主题身份正确。

## 2) 会引入的新风险／回归

1. **高：`radar-board` 与 `dark-board` 会制造不可判定的自动路由。**  
同一份“暗色情报监测报告”同时命中两者；自然语言路由没有互斥规则，LLM 会跨运行随机选主题，导致结果不可复现。

2. **高：暗色 CSS 无法自动修复 ECharts 内部配色。**  
反例：scatter 的轴线、标签、tooltip、legend 仍使用浅色主题默认配置，在深色背景上近乎不可见；仅验证 CSS 指纹和 HTML 结构发现不了。

3. **高：指纹测试只能证明字符串存在，不能证明级联真正生效。**  
反例：`POST-SHARED OVERRIDE` 顺序错误导致共享样式覆盖主题变量；注释、字体变量和底色变量都在文件里，pytest 全绿但页面实际使用错误颜色。

## 3) 被忽略的更优或更简单替代方案

1. **先只交付 `forest-editorial`；`radar-board` 直接作为 `dark-board` 的覆盖配置验证。**  
只有在固定 DOM 上产生稳定、可测的结构外差异后才给独立主题名，避免先引入路由歧义再靠主观截图决定回滚。

2. **用一份冻结的 HTML 全组件夹具做换肤，而不是让 AI 各生成一份样张。**  
同一 DOM 覆盖 hero、KPI、表格、timeline、scatter，再切换 CSS 截图；这才隔离主题变量，也能直接验证图表可读性和内容零变化。

## 4) 若只允许先做一件事

1. **先建立冻结 HTML 的 `dark-board / forest-editorial / radar-board` 三方截图对照。**  
它一次性验证最核心的 CSS-only 假设、`radar-board` 独立价值及暗色图表可读性；这三项不过，五处内置联动做得再完整也只是把无效主题正式化。
